つづり｜TSUZURI / 2026-10-17

フィッシングはURL確認だけで防げる？キリル文字から考える、見抜く力に頼らない対策

URLを見て確認したのに、見抜けない。だったら「もっと気をつけて」で終わらせず、確認する流れを変えたいですよね。キリル文字の仕組みから、受け取る側・送る側でできることを、僕なりに考えてみました。

Main Actor 神藤 俊希 / Speaker —

情報管理AIリテラシー医療介護産業保健週末のAI整え習慣

今回の話で、僕が一番怖いなと思ったのは、「URLを見て確認すれば大丈夫」という対策が、それだけでは通用しないことなんですよね。怪しい文字の羅列だったら気づけても、いつもの文字とほとんど同じに見えたら、どうでしょうか。

「ちゃんと確認したから大丈夫」と思った人も、そこで止まってしまうかもしれない。だから、見抜く力だけに頼らない流れへ、変えていく必要があると思うんです。メールのリンクはいったん触らず、いつもの公式アプリや、正しいと確認して登録したブックマークから開く。まずは、その習慣を考えたいです。

TAYORI・IROHAの有効な会員の方は、会員ページで最新号・バックナンバーを確認できます。

10月17日の「週末のAI整え習慣」でも話した内容です。共有された投稿が指す個別の事件については、発生や経緯まで確認できていません。ここではUnicode・ICANN・IPAの資料を見ながら、仕組みと対策を整理して、そこから僕が考えたことを書いていきます。

キリル文字って、そもそも何なのか

キリル文字は、ロシア語やウクライナ語などの表記に使われる文字体系です。英語などのラテン文字とは別の文字ですが、一部に字形の似たものがあります。例えば、ラテン文字の「a」はU+0061、キリル文字の「а」はU+0430です。大文字でも、ラテン文字の「A」はU+0041、キリル文字の「А」はU+0410で、それぞれ別の文字として符号が割り当てられています。U+で始まる番号はUnicodeのコードポイントです。

見た目は似ていても、コンピューターには別の文字なんですよね。使うフォントによって、似て見える度合いも変わります。Unicodeのセキュリティ仕様は、文字列のこうした視覚的な混同を扱っています。原典：Unicodeのキリル文字表／Unicode Security Mechanisms（識別子と似た文字の検出）

日本語などを含め、さまざまな文字をドメイン名に使う仕組みが国際化ドメイン名（IDN）です。似た字形を悪用して別のドメインを本物のように見せる手口は、IDNホモグラフ攻撃と呼ばれます。キリル文字や多言語のドメイン自体が危険なのではありません。ブラウザーや登録側にも対策があり、常に同じ表示になるわけではありませんが、利用者による目視だけを安全判断の根拠にしないことが大切です。

ICANNは2005年にも、この問題を取り上げています。なので、今回AIが初めて生み出した手口だとは言えないんですよね。原典：ICANNのIDNホモグラフ攻撃に関する説明

少し知っているからこそ、安心してしまわないか

ここで気になったのが、何も知らない人だけの話ではない、というところです。「変なドメインじゃないか確認する」と知っている人ほど、本物っぽく見えたときに「確認できた」と思ってしまうかもしれない。僕は、そこが怖いなと思ったんですよね。知識がいらないという話ではなくて、知っている対策も更新していかないといけないということです。

ただ、「少し知識がある人が一番引っかかる」とまで言えるデータは、今回確認できていません。誰が危ないかを決めたいのではなくて、僕自身も「知っているから大丈夫」で止まらないようにしたい、という話です。

この記事の要点

URLを見たことと、安全だと確かめられたことは、同じではないんですよね。見抜けないこともあると考えて、メールから離れて確認する習慣と、戻れる入口をセットで用意しておきたいです。

文字の違いを毎回探すのは難しそう。いつもの入口から確かめる方法を覚えたいな。

メールのリンクを押す前に、いつもの入口へ戻る

IPAも、普段のブックマークや正規アプリから開く方法を案内しています。アカウント停止、請求、支払い、本人確認、健康情報の入力。こういう大事な操作を求められたら、僕はまずメールのリンクを使わずに確かめる流れにした方がいいと思います。IPAの案内はこちらです。

差出人の名前に見覚えがあっても、それだけで今回の依頼まで本物とは限りません。メールに書かれた電話番号へかければ安心、でもないんですよね。以前から確認してある入口や連絡先に戻る。検索広告も、そのまま正規の入口だと決めつけないようにしたいです。

実践チェック｜まず変えたい4つの行動

  1. 重要な手続きを促すメールが来ても、メール内のリンクはいったん使わない。
  2. 正規アプリや、正しいと確認して登録したブックマークから開く。
  3. 公式サービスの通知・履歴と照合する。見当たらなくても、それだけで偽物と断定せず既知の窓口に確認する。
  4. 判断できなければ止まって相談する。既に入力・ダウンロードした場合も、責められることを恐れず組織の対応窓口へ速やかに報告する。

「急いで」と書いてあっても、いったんリンクから離れよう。相談先も一緒に決めておくと動きやすいね。

「気をつけて」で終わらず、職場の流れも変えたい

職場でも、「気をつけましょう」と言うだけだと、忙しいときにどう動けばいいかが残らないですよね。請求書や健診予約、アカウント更新なら、どこで確かめるのか。分からなければ誰に聞けばいいのか。僕は、そこまで一緒に用意しておくのが大事だと思っています。急ぎの依頼でも、確認のために少し止まっていい。そういう流れにしておきたいです。

組織側では、迷惑メール対策、ソフトウェアの更新、多要素認証、必要最小限のアクセス権、事故時の連絡経路などを担当者と組み合わせて考えてみます。どれか一つで被害をゼロにできるわけではありません。メールの見分け方だけを繰り返す研修から、架空のメールを使って「どこに戻り、誰に相談するか」まで練習する研修へ変えていくことも提案したいです。

医療・介護では患者・利用者の情報、産業保健では職員の健康情報や本人確認情報を、確認のために新たな送信先へ渡さないことも大切です。不審メールを外部AIへ丸ごと貼ると、含まれている機微な情報まで送信する可能性があります。組織で定めた報告・相談経路を使います。

そうなると、メールを送る側も考えないといけないですよね

一方で、みんながメールのリンクを押さなくなったら、メルマガを送る側はどうなるんだろう、とも思うんです。クリック数だけでは、ちゃんと届いているかが分かりにくくなるかもしれない。これは僕の考えで、今回の手口によってクリック率が下がったと確認したデータがあるわけではありません。

そうなると、「信用して押してください」だけでは難しいですよね。公式サイトにも同じ案内を載せておく。メールには記事名や開催日、どこから探せるかを書いておく。ログインや健康情報の入力は、公式の画面からできるようにしておく。こうしておけば、受け手は自分が知っている入口から確かめられます。

本物っぽく見せるだけではなく、別の入口からも確かめられるようにする。受け取る側の対策が変わるなら、送る側の案内の仕方も変えていく必要があるんじゃないかなと思っています。

見抜けなかった人を責めるより、立ち止まって相談できる手順を整えたいですね。どこへ戻れば安心して確かめられるでしょうか。

見抜けなかった人に「もっと気をつけて」と言うだけでは、同じことを繰り返してしまうかもしれません。見抜けない自分でも、一度止まって、確かめられるようにしておく。まずは、よく使うサービスの正しい入口と、困ったときの相談先を一つ確認するところからでいいと思うんですよね。
