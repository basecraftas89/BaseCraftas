## 検証

今回の確認結果：追加セキュリティテスト14件と既存回帰テストが成功（Nodeテスト集計15/15）。Worker dry-run、workerdでのローカル実行、構文検査、差分の空白検査も成功。本番反映後の確認は未実施。

- `npm test`：サイトビルド、既存回帰テスト、追加セキュリティテスト。
- `npm run check:worker`：Wranglerの本番送信なしビルド。
- `node scripts/check-worker-runtime.mjs`：直前のdry-run出力をworkerdで実行し、ローカルD1への保存と安全化を確認。ローカルポートの起動が必要。
- `node scripts/plan-media-migration.mjs snapshot.json published-json-directory /private/tmp/media-plan.sql`：移行SQL案のみ生成。ネットワーク通信・DB更新なし。

Wranglerのログ書込先を制限した環境では `WRANGLER_LOG_PATH=/private/tmp/hp-wrangler.log` を設定してください。

## 本番反映前に必ず揃えるもの

1. **最新の公開記事を取得したリリース元。** ローカルには未コミット変更が多数あります。GitHub main上の最新記事HTML/JSONを取り込み、今回の差分を統合・確認すること。現状のローカルフォルダをそのままアップロードすると、別途公開された記事や他の変更を取りこぼすおそれがあります。
2. D1のバックアップ、R2の対象画像一覧、現在のWorkerの版、Pagesの直前デプロイ情報。
3. 編集者の未共有原稿を保存・退避。sessionStorage移行後はタブを閉じると未共有原稿が失われます。旧localStorageはログインメールが一致する場合に未共有原稿だけ移行して削除します。所有者を識別できない旧キャッシュは自動破棄しません。所有者が旧画面で退避し、新画面の「端末の保存を消してログアウト」で消去してください。
4. 画像の移行案。新しい公開画像テーブルは空のため、移行せずWorkerだけ反映すると、既存R2画像は一般公開されなくなります。

## 画像移行の作り方

編集・公開を一時停止し、D1から記事・画像のスナップショットと、GitHubの**現在公開している**`projects/totonoe/data/contents/*.json`を取得します。保存先はサイトフォルダ外にしてください。

`snapshot.json`は次の形です。D1のエクスポート結果をこの形へ整理します。秘密情報は不要です。

```json
{"articles":[{"id":"article_...","status":"published","deleted_at":null}],"assets":[{"r2_key":"contents/...","article_id":"article_...","content_type":"image/png"}]}
```

移行ツールは公開JSONのアイキャッチ・本文画像だけを対象にSQLを作ります。公開されていることが確認できる未紐付け画像は記事に結び直します。SVG、別記事と共有する画像、欠けたデータは`.issues.json`へ出力し、自動処理しません。共有画像は利用先ごとに再アップロードする等の確認が必要です。未解決のある移行案をそのまま適用しないでください。

## 反映する順序（未実施）

1. 最新の公開データと統合済みコードでテスト・ビルドし、表示を確認。
2. 編集・公開を一時停止。バックアップを確保。
3. D1へ`apps/column-studio-api/migrations/20260911_security.sql`を適用。その後、確認済みの画像移行SQLを適用。
4. Cloudflare Pagesをビルドコマンド`npm ci && npm run build`、出力`dist`へ変更。Direct Uploadの場合も`dist`だけを指定する。
5. 静的管理画面とWorkerを同じ改修版で反映。片方だけの状態では編集を再開しない。
6. 旧ソース・設定ファイルと`/column-media/*`のCDNキャッシュを削除。以前の画像には1年のキャッシュ指定があったため、新ヘッダーだけで既存コピーを即時失効させられるとは限らない。
7. 本番チェックを行い、編集を再開。

既に閲覧者へ渡ったファイルやブラウザに長期キャッシュされた画像は、サーバー側だけでは回収できません。機密画像が存在した場合は別途判断が必要です。

## 本番チェック

- 未認証の管理画面・本人確認API・記事一覧APIはAccessログインへ。`pages.dev`、旧デプロイ、プレビューURLも公開範囲を確認。
- `/apps/column-studio-api/src/worker.js`、`schema.sql`、`wrangler.toml`、`README.md`、この手順書が一般公開されていない。
- 管理者・編集者・閲覧者で、それぞれ保存・閲覧・公開の許可が正しい。
- 記事の吹き出し・強調色・画像・プレビュー・履歴が維持される。
- 新規画像は記事保存後にアップロードでき、管理画面で表示できる。公開前は一般取得不可、公開後は表示、非公開後は取得不可。
- 公開済み記事に新しい下書き画像を追加しても公開操作までは一般取得できない。
- 危険な本文・SVGが拒否または除去される。最後の管理者は登録・更新のどちらでも失われない。
- 問い合わせフォーム・動画・音声埋め込みがヘッダー変更後も動く。
- 本番の応答にヘッダーが適用されている。

## 残る対策・制約

- **管理画面・メディアの別オリジン化は未実施。** DNS、Access、Workerルート、公開URLの変更を伴うため、移行先ドメインと認証設定を揃えて別工程で行う。今回は同一オリジン内でサニタイズ・厳しい管理CSP・画像の能動コンテンツ拒否・認証経路分離を実装。
- 画像の識別情報チェックは、完全なデコード・再エンコードではない。画像再エンコードサービスを使う場合は新しいbinding等の設定が必要。配信MIME固定・nosniff・sandboxは実装済み。
- 既存R2のSVG棚卸し・変換、孤立画像の削除は未実施。自動的に消すと原稿を失うため、移行時に確認して実施する。今後の新規アップロードは記事ID必須。
- APIの回数制限はアカウントごと。未認証の大量アクセス防御はAccess/WAFの設定を確認する。
- 公開サイト全体の`script-src`制限は段階導入が必要。今回は管理画面に適用し、公開サイトは既存埋め込みを壊さない基礎CSPに留めた。
- MFA、Google Forms回答の共有範囲、AccessとD1の退任者処理、トークンの権限と更新、バックアップの復元、失敗通知は管理設定・運用体制の確認が必要。実設定は変更していない。
- 古いD1本文・履歴は非破壊で残し、読み出し時にも安全化する。既存公開記事は最新データを取得してビルドまたは再公開するまで変わらない。
